# 第一个样板带来的流程修订

本页记录 2026-08-14 完成首个 Codex CLI `hi-en-v1` 样板以后，对人工测试流程做出的修订。

## 样板之前的假设

最初方案倾向于把每次运行都做成完整证据包：每次重复采集版本、系统、订阅、空目录、启动界面、运行前后状态、回复和 usage。

真实走完一次以后发现，这会让贡献者反复截取没有变化的环境信息，增加操作量，也更容易误操作。

## 实测中发现的问题

### 环境证据不应重复三遍

同一场景的 Agent 版本、模型、effort、订阅、操作系统和固定 harness 配置在三次连续运行中没有变化。它们属于场景，不属于单次 attempt。

修订后，场景级证据只采一次。每个 attempt 只要求输入与回复证据、原生 usage 证据；能够取得机器事件时，再由脚本提取模型、effort、缓存和时间。

### 证据不能放进被测工作区

早期 pilot 把截图保存进测试目录，导致目录不再严格为空。虽然模型没有读取文件，但这违反了空目录场景的形式要求。

修订后，原始证据始终保存在测试工作区之外。公开包只在运行全部结束以后生成。
开始采集前还应确认截图、终端日志和临时导出的默认保存位置均指向工作区外，不能先写入空目录再移走。

### 空目录不等于空上下文

三个工作区里都没有项目文件，也没有 `AGENTS.md`，但 Codex 仍然注入了产品基础指令、skills、权限与文件系统描述、日期时区和工作区路径；内置工具定义是否完整暴露给日志则无法确认。

因此，“空目录里的 `hi`”测到的是最小项目上下文之上的完整 Agent harness，不是两个可见字符单独发给裸模型的 API 请求。工作区命名也应使用固定格式，避免路径长度变化成为额外噪声。操作系统和架构继续作为场景变量记录，即使目前没有证据证明它们一定改变用量。

### 不要在首个 prompt 前退出再恢复

早期 pilot 在输入前执行了 `/quit`，随后恢复会话。它被保留为 pilot，但不进入三次标准重复。

标准 fresh 场景要求从新会话直接进入第一次模型请求；任何 resume 都必须另标为 `resumed` 场景。

### 两个 total 不是同一个口径

Codex 0.147.0 的事件日志中，`input_tokens` 包含 cached input；退出界面则把非缓存 input 和 cached input 拆开，并用非缓存 input 加 output 显示 `total`。

因此样板同时保留：

- `context_total_tokens`：包含 cached input 的输入总量加输出；
- `cli_total_excluding_cached`：CLI 退出界面口径，即非缓存输入加输出；
- `cached_input_tokens`：单列，不隐藏在任何 total 后面。

`cli_total_excluding_cached` 不是订阅额度成本。OpenAI 公开说明缓存读取与普通输入的处理不同，并建议分别跟踪缓存字段，但没有公开 Codex Pro 订阅额度的精确换算公式。[OpenAI GPT-5.6 模型指南](https://developers.openai.com/api/docs/guides/latest-model)

### UI 与事件日志冲突时都保留

运行前 `/status` 曾显示 `1M` context window；请求后的事件日志报告 `258400`，UI 随后显示约 `258K`。样板没有擅自选择其中一个，而是把它登记为可观察到的口径变化。

### 共享额度不能随意归因

测试期间同一订阅还有其他任务运行，因此 weekly limit 的任何变化都标记为 contaminated。每个 Session JSONL 的 token 仍可归因于各自运行，但共享额度百分比不能归因于某一句 `hi`。

### Hooks 要区分“存在”与“额外调用模型”

本场景保留了本机通知和记录 hooks。经本地代码检查，它们只处理已有回复或元数据，没有再请求模型；因此不会把另一次模型调用混进本 session 的 token，但这个判断在公开包中只能标为 `self_reported`。

后续贡献应同时记录 hook 是否启用、触发时机和是否会调用模型。会调用模型的 hook 属于 harness 成本；只做本地通知的 hook 也应披露，但不能仅凭“收到了摘要通知”就推断发生了第二次推理。

## 修订后的最短流程

一个场景至少顺序执行三次。

场景级只做一次：

1. 记录 Agent、版本、OS、架构和 UTC 时间；
2. 证明订阅、路由、模型、effort 和 harness；
3. 保存共享证据。

每次 attempt：

1. 新建独立空目录和 fresh session；
2. 只发送一次精确输入；
3. 保存输入与完整回复；
4. 正常退出并保存原生 usage；
5. 能够取得时，生成精简事件日志。

如果 attempt 无效，不删除它，也不拿另一次结果悄悄替换；保留原因并继续追加，直到至少有三次有效运行。

缺少某项证据不阻断贡献，但必须标记。没有被验证的字段不能进入强结论或“已验证字段”统计。

## 第一个样板的主要结果

三次标准运行的输入总量都为 13,950 tokens；包含 cached input 的上下文总量为 13,963–13,964。缓存命中从 0 到 9,984 tokens 不等，使 CLI 退出界面的 total 从 3,980 到 13,963 变化。

这说明首个样板最值得记录的并不是一个孤立的数字，而是同一 harness 的固定上下文规模，以及缓存状态如何改变产品显示的 token 口径。

## 下一轮最值得自动化的部分

首个样板之后，适合优先自动化的是机械步骤，而不是让脚本替贡献者猜字段：

1. 一次生成场景目录、三个等长命名的空工作区和证据目录；
2. 自动采集版本、OS、架构、UTC 时间和 prompt 哈希；
3. 从原始 session 日志确定性提取最小事件，并明确区分 source 与 derived 字段；
4. 自动检查至少三次有效运行、精确 prompt/response 哈希、公开文件哈希和常见隐私线索；
5. 最后再生成结果索引和可视化。

模型、订阅、effort、路由和隐私判断仍需要视觉证据或人工复核。过早做“全自动成本排名”会掩盖产品之间完全不同的用量口径。
